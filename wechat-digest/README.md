## 二、密钥提取：为什么老工具全失效

微信 **4.1.11+** 改了密钥缓存格式，导致所有基于 `x'<64位hex>'` 内存扫描的工具全线失效：

1. **不再明文缓存**。密钥以 `x'<64位hex key><32位hex salt>'` 形式存放，**共 96 位 hex**（99 字节含首尾引号）。老正则要求恰好 64 位后紧跟 `'`，第 65 个字符是 hex 而非引号，**永远匹配不到**。
2. **整段被 XOR 混淆**。32 字节循环掩码：
   `d2c7442458020000004889442450488b450048844c2448488944254048584c24`
   所以即使搜 ASCII `x'` 也找不到。
3. **这段 blob 嵌在对象图里**，公开工具靠 `com.Tencent.WCDB.Config.Cipher` 对象的内部结构偏移（`0x88`/`0x28`/`0x10` 等）定位，换个小版本就可能失配。

### 本工作区采用的办法：相位扫描（与版本无关）

既然 blob 整体按 `mask[i % 32]` 逐字节 XOR，而 blob 在内存中的起始位置未知，
就把「blob 起点相对当前位置的相位」0..31 全部枚举：对每个相位构造混淆后的 `x'` 两字节特征
并全内存搜索，命中后按同一相位向后解码，要求解出 `x'<>=64位hex>'`。

**不需要任何结构偏移**，只要那段字符串在内存里就一定能找到。
（先用「后 4 字节解码后必须是 hex」预筛——2 字节特征在 GB 级内存里会有几十万次随机命中。）

### 校验标准

**命中不等于正确**。唯一可信判据是 SQLCipher 4 每页自带的 HMAC：

```
mac_salt = salt XOR 0x3a
mac_key  = PBKDF2-HMAC-SHA512(enc_key, mac_salt, 2, dklen=32)
HMAC-SHA512(mac_key, page1[16:4032] + LE32(1)) == page1[4032:4096]
```

注意：Config.Cipher 里的 64 位 hex **就是可直接使用的 enc_key**，不需要再跑 256000 轮 PBKDF2
（那条路是针对"只有 passphrase"的旧情况）。

## 六、第 3 步：已完成（会话映射 + 发送者语义）

### 结论一：表名 = `Msg_` + `MD5(user_name)`

MD5 **区分大小写**（用 `MD5(lower(u))` 只能命中 493/496，必须用原样 `user_name`）。
`message_0.db` 的 496 张会话表 **496/496 全部可解释**，无残留表。

### 结论二：`real_sender_id` 就是该 shard 的 Name2Id rowid

网上流传的「旧库 `real_sender_id` 是会话内角色 1/2，且不同库 1/2 含义可能相反」
**在本机不成立**。证据是硬性的——`real_sender_id` 的最大值恰好等于该 shard 的 Name2Id 行数：

| shard | Name2Id 行数 | real_sender_id 最大值 | 本人 rowid | 会话表 |
|---|---|---|---|---|
| message_0.db | 1726 | 1726 | 2 | 496 |
| message_1.db | 7 | 7 | 2 | 6 |
| message_2.db | 3 | 2 | 2 | 2 |
| message_3.db | 143 | 143 | 2 | 37 |
| biz_message_0.db | 87 | 87 | 2 | 68 |

若真是「角色 1/2」语义，最大值不可能达到 1726 或 143。`message_1/2.db` 里看到的 1/2，
只是**恰好 rowid=1（对方）与 rowid=2（本人）撞上了 1 和 2**——这正是它最容易被误判之处。

**但工程上仍必须逐库解析**：每个 shard 有自己独立的 Name2Id，rowid 分配互不相同。
本人 rowid 要用 `user_name == 自己的 wxid` 反查，**不要硬编码 2**。

## 七、第 4 步：WAL 核查（已闭环，结论：无需合并）

备份是微信运行中做的，所以最初担心 `message_0.db-wal`(4 MB)、`message_3.db-wal`(2.5 MB)
里的最新消息还没进主库。**实测结论：这个担心不成立，那些 WAL 帧是环形缓冲区的旧世代残留。**

### 证据一：主库本来就是最新的
备份在 **10:59** 完成，每个主库的最大 `create_time` 与它自己的文件写入时间几乎一致：

| 库 | 消息数 | 最新消息 | 文件写入时间 |
|---|---|---|---|
| message_3.db | 1,238 | 2026-10-09 10:59:47 | 10:59:57 |
| message_0.db | 187,799 | 2026-10-08 10:41:22 | 10:41:50 |
| biz_message_0.db | 3,501 | 2026-10-09 10:04:52 | 10:05:07 |

`session.db` 的 `SessionTable.last_timestamp` 同样是 10:59:47，与之一致。

### 证据二：WAL 里全是旧世代帧
每个 WAL 内部含 **1–14 个不同 salt 世代**（`message_3.db-wal` 8 个、`biz_message_0.db-wal` 8 个、
`head_image.db-wal` 14 个）——典型环形缓冲区残留多代旧帧。按 SQLite 自身规则
（帧头 salt ≠ WAL 头 salt → 该 WAL 无效），这些帧**本来就该被忽略**。

### 证据三：强行应用会损坏数据库
`tools/analyze_wal_generations.py` 实测两种策略，全部失败：

| 库 | 基线 | 应用全部帧 | 仅末世代 |
|---|---|---|---|
| message_0.db | 187,799 条，quick_check=ok | **185,453 条，报损坏** | **185,453 条，报损坏** |
| message_3.db | 1,238 条，quick_check=ok | **1,015 条，报损坏** | **1,016 条，报损坏** |
| biz_message_0.db | 3,501 条，quick_check=ok | 重复索引，打不开 | 重复索引，打不开 |

消息数**变少**说明这不是"补上最新消息"，而是把数据库回滚到旧状态。注意这些页**都能通过
逐页 HMAC 校验**（确实是本库的真页）——所以「HMAC 通过」只是必要条件，不是充分条件。

### 副产品：分片轮换规律（对流水线很重要）
活跃分片是 **`message_3.db`，不是 `message_0.db`**（与网上说法相反）。时间线连续无缝：

| 分片 | 时间跨度 | 消息数 |
|---|---|---|
| message_2.db | 2024-03-19 → 2024-10-06 | 698 |
| message_1.db | 2024-10-06 → 2025-10-05 | 1,185 |
| message_0.db | 2025-10-09 → 2026-10-08 10:41:22 | 187,799 |
| message_3.db | 2026-10-08 10:42:11 → 2026-10-09 10:59:47 | 1,238 |

⇒ **流水线绝不能假设 `message_0.db` 是最新的，必须按 `create_time` 跨全部分片取数。**

`tools/merge_wal.py` 已按上述教训加固：只接受与 WAL 头 salt 一致的当前世代帧，
且合并结果必须通过 `PRAGMA quick_check` 才允许保留，否则自动回退为未合并版本。
当前所有 WAL 都被正确跳过，输出与未合并版本**逐字节一致（24/24）**。

### 导出正文时又踩到 5 个解析坑（已全部固化进 `tools/export_conversation.py`）

1. **`local_type` 是 64 位打包值**：低 32 位=类型，高 32 位=子类型。
   `244813135921` = `(57<<32)|49` → 类型 49（appmsg）的子类型 57（引用回复）。
   按整数直接查类型表会看到一堆"未知类型"。
2. **群消息的 `message_content` 带发送者前缀** `wxid_xxx:\n实际内容`，必须剥掉。
3. **type 49 的 XML 本身就是 ZSTD 压缩帧**，存在 `message_content` 里（**不是** `compress_content`，
   该列在本机全为空）；且帧头常缺 FCS，`ZSTD_getFrameContentSize` 返回"未知"，
   必须用 `ZSTD_decompressBound` 或逐步扩容。已用 Git 自带 `libzstd.dll` 走 ctypes 解决，
   **无需 pip 安装 zstandard**。
4. **群昵称不在 `chatroom_member`**（该表只有 `room_id`/`member_id`）。群昵称只出现在引用回复
   XML 的 `<refermsg><displayname>` 里；用"谁引用了我"可反推本人在该群的昵称，才能识别 `@我`。
5. **引用显示名 ≠ 联系人显示名**：引用里是群昵称（如"星星之火－谋求转行ing－北京"），
   行首用 `contact.remark`/`nick_name`（如"原"）。同一人两个名字会让"活跃人数"统计偏大，
   摘要里已如实标注。

### 附带成果：微信 4.x 图片解密（已完成）

原本摘要里 43 张图片「不可读」，现已打通。关键事实：

- **格式**：本机 71,424 个 `.dat` 全部是 **V2**（`07 08 56 32 08 07`），没有 V1/旧 XOR 格式。
  V2 布局 = `[6]magic + [4]aes_size + [4]xor_size + [1]保留`，然后 AES-128-ECB 段
  （从 offset **15** 起，长度按 16 字节向上取整、PKCS7 填充）、明文段、末尾 `xor_size` 字节的
  单字节 XOR 段。
- **密钥**：AES `b58a8ac8f156b232`（16 字符 ASCII，从 `Weixin.exe` 内存扫出）、XOR `0x4e`。
  两个都有**密码学判据**，不是猜：候选 AES 密钥必须能把密文块解成 JPEG/PNG 魔数；
  XOR 密钥必须能让文件尾变成 `FF D9`。
- **消息 XML 里的 `<img aeskey>` 不能解本地文件**（那是 CDN 下载密钥），实测 203 个候选**零命中**。
- **`wxgf` 是微信自有的 HEVC 容器**（偏移 42 处有 NAL 起始码）。本机无 ffmpeg、无 HEVC 扩展，
  这批全分辨率原图**读不了**。
- **但不必读它**：同一张图在 `cache\<月>\Message\<会话hash>\Bubble\*_b.dat` 里还有一份
  **JPEG 显示版**，同一密钥可解，实测 **150/150 全部可解码**。
  后缀含义：`_t`=缩略图(180px)、`_b`=显示原图、`_h`=高清、`.wxgf`=HEVC。**取图优先用 `_b`**。
- **会话归属天然可得**：`msg\attach\<md5(会话 username)>\<月>\Img\`，
  该 hash 与 `Msg_<hash>` 表名同源。
- **验证方式**：解出来必须能被真实图形库解码（用 .NET `System.Drawing` 读宽高），
  只看魔数不够——有一张 PNG 魔数正确但实际已损坏，被严格校验抓出来了。

成果：`tools/find_image_key2.py`（取密钥）、`tools/decrypt_dat.py`（批量解密）、
`keys/image_key.json`。首份收益见炒饭会摘要新增的「图片内容补充」一节——

### 这一批暴露出的两个能力缺口（已查证，附结论）

**1）语音内容读不了 —— 关键答复可能只存在于语音里**

而「拆模时间」这个装修进场的前置答复**只在语音里**，文字记录完全没有。
查证结果：语音以 **SILK 原始音频**存在 `media_0.db` 的 `VoiceInfo.voice_data`
（表头 `#!SILK_V3`），消息 XML 里只有 `voicelength`/`voiceformat`，**库内没有转写文本**。
要读语音需要 SILK 解码器 + ASR 模型，两者都依赖联网安装，而本机网络被拦 —— **暂时无解**。
（可替代：摘要里显式列出「哪些结论只在语音中」，提醒人工复听，本项目已这样做。）

**2）图片无法精确归属到消息**
图片消息 XML 里确实有 `md5` 与 `originsourcemd5`，但把它们在整个账号目录里搜索是
**零命中** —— `.dat` 文件名用的是另一套哈希，**精确映射不可得**。
退而求其次的做法是时间邻近匹配（土建群首张图与消息仅差 3 秒，置信度高；
其余受下载延迟影响，可能差 20 分钟~1.5 小时），**必须标注为推断**。
另一个覆盖缺口：`Bubble\*_b.dat` 只包含**实际渲染过**的图片
（云锦小学窗口 38 条 `[图片]` 只解出 13 张），未渲染的图没有 JPEG 显示版可用。

4. **`zstandard` 缺失**。pip 网络在本机被拦（`raw.githubusercontent.com` 与 PyPI 均不通），消息内容若有 ZSTD 压缩**无法解压**。备选：Git 自带的 `C:\Program Files\Git\mingw64\bin\libzstd.dll`（可用 ctypes 调用 `ZSTD_decompress`），或 Node v24 的 `zlib.zstdDecompress`。

## 十、网页工作台（每小时自动刷新）

**地址：http://127.0.0.1:8765/**（只绑本机回环，外部访问不到）

启动方式二选一：

```powershell
python tools\workbench_server.py --port 8765     # 命令行
workbench\启动工作台.cmd                          # 双击启动（会顺带打开浏览器）
```

### 刷新机制（两层，必须分清）

| 层 | 频率 | 内容 |
|---|---|---|
| 数据刷新 | 每小时（实测增量 **8.9 秒**） | 备份 → 密钥校验 → 解密 → WAL 完整性门禁 → 会话映射 → 活跃度 → 汇总索引 → 图片解密 |
| 页面刷新 | 每小时（另有倒计时与手动按钮） | 重新拉 `/api/*`，不整页重载 |

**摘要本身需要 LLM，无法无人化。** 工作台为此专门做了过期标注：
「会话索引」里带 <kbd>摘要已过期</kbd> 的会话，表示它的摘要窗口之后又来了新消息
（当前是云锦小学大三班、周静两个），需要让 Agent 重跑那两个会话的摘要。

### 架构：展示层不碰数据库

```
refresh_pipeline.py  →  out/status.json  →  workbench_server.py  →  浏览器
      （重活）              （唯一契约）          （只读+HTTP）
```

`status.json` 是唯一契约：页面永远秒开，也不会因为查询把数据库搞坏。

### 接口

| 路径 | 说明 |
|---|---|
| `GET /` | 工作台页面（单文件，无 CDN 依赖） |
| `GET /api/status` | 快照时间、管线步骤与耗时、密钥状态、会话列表（含 `stale` 标记）、摘要列表 |
| `GET /api/todos` | 从最新汇总里抽出的「待我处理」总表 |
| `GET /api/digests` / `GET /api/digest?file=` | 摘要列表 / 摘要正文 |
| `GET /api/images` / `GET /img/<组>/<文件>` | 已解密图片清单 / 图片本体 |
| `POST /api/refresh` | 手动触发一次数据刷新（后台线程，不阻塞页面） |

安全：仅监听 `127.0.0.1`；所有文件访问都做目录穿越校验与扩展名白名单（仅图片格式）。

### 登录自启（已配置并实测）

**Windows 计划任务（`schtasks`）用不了**——创建任务要写 `C:\Windows\System32\Tasks`，
需要管理员权限，本机当前是标准用户，实测报 `Access is denied`。

改用**用户级启动目录**（无需管理员）：

```
C:\Users\LL\AppData\Roaming\Microsoft\Windows\Start Menu\Programs\Startup\微信重点工作台.lnk
  Target : ...\Python312\pythonw.exe

  WorkDir: G:\dsh\wechat-digest
```

用 `pythonw.exe` 是为了**完全不弹控制台窗口**。
实测：用该快捷方式拉起后，首页与 `/api/status` 均返回 200，服务可用。

> 注意一个环境特性：从**沙箱托管的 shell** 里启动的子进程，会在该 shell 退出时被一起回收
> （所以从命令行 `Start-Process` 起的实例活不久）。登录时由 explorer 启动不受此影响。

### 渲染器上踩的两个坑（都体现为"页面看起来没坏，但内容是错的"）

写 `test_renderer.cjs` 的价值就在这里——它抓出了两个**只靠肉眼看不出**的问题：

1. **跨行粗体失效**：逐行解析时 `**...**` 若跨越换行就永远配不上，会残留字面 `**`。
   已改为"本行 `**` 个数为奇数就与后续行合并后再解析"，并让粗体正则用 `[\s\S]+?` 跨行匹配。
   表格行不参与合并，否则会把表格拆坏。
2. **行内代码被粗体正则吃掉**：摘要里有 `sk-c78d****f297` 这类脱敏 Key，
   星号是**真实内容**。原实现先跑粗体正则，会把这段星号误当定界符、
   把整行后面的文字吃成一坨粗体。已改为**先抽出代码段占位、处理好粗体/链接后再还原**。

> 顺带一个方法论教训：这个测试**第一版报了 3 类假失败**——对输入里根本不存在的语法
> （某些摘要没有 `###` / `>` / 列表）也断言要有输出，以及在代码段里找残留的 `**`。
> 断言必须**条件化**（输入有才要求输出有）并**排除代码段**，否则是在惩罚正确的实现。

## 十一、踩坑记录：端口 8765 会被 DSH 自己抢占

**现象**：工作台页面能打开、能显示倒计时，但点「立即刷新数据」报"触发失败"。

**根因**：我最初随手把服务端口定为 **8765**，而 DSH 自身有一个文件服务
（`present()` 的浏览器交付）也会**监听 0.0.0.0:8765**，响应头是
`Server: SimpleHTTP/0.6 Python/3.12.10`，由 `python.exe` 承载。
当我的服务死掉、8765 空出来后，它抢占了该端口。

于是浏览器访问 8765 打到的**不是我的服务**，而那个服务器不支持 POST，
`POST /api/refresh` 返回 **501 Unsupported method**，前端 fetch 抛错 → "触发失败"。

**修复**（三层，缺一不可）：

1. **不再用 8765**：`PORT_CANDIDATES = [18765, 18766, 18767, 18888]`，默认避开。
2. **占用者判别不能只看"端口是否被占"**：`probe_ours()` 改为请求 `/api/status`，
   只有能返回带 `state` 的 JSON 才认定是自己的实例。否则会把别人的服务误判成自己，
   导致守护进程直接退出、真正的服务永远起不来。
3. **实际地址写入 `out/workbench.url`**：端口是动态的，启动器读这个文件再打开浏览器，
   避免打开到旧端口。
4. **前端加心跳**：每 20 秒探测一次，失联时弹红色横幅明确告知"服务已停止，
   请双击 启动工作台.cmd"；刷新按钮改为轮询到刷新真正结束并显示进度。

**已实测**：8765 被占的情况下，服务自动改挑 18765；
`POST /api/refresh` 返回 200，约 9 秒后管线完成（`last_pipeline_ok=True`）。

## 十二、一个必须知道的环境限制：常驻进程无法由 Agent 拉起

**现象**：工作台页面过一段时间会变成 `ERR_CONNECTION_REFUSED`。

**根因**（实测确认，不是代码 bug）：**Agent 所在的沙箱会在每次工具调用结束时，
杀掉该次调用创建的所有进程。** 三种脱离手段全部试过，均无效：

| 手段 | 结果 |
|---|---|
| 托管后台任务（job） | 会话跨夜/上下文回收后任务消失，服务随之消失 |
| `explorer.exe <脚本>` | explorer 只把参数当路径打开，**不执行**脚本 |
| `Shell.Application.ShellExecute`（进程外 COM，宿主 explorer） | 能起来、能服务（HTTP 200），**但调用一结束仍被杀** |
| `schtasks` 计划任务 | 需管理员，当前标准用户 `Access is denied` |
| WMI `Win32_Process.Create` | `Access denied` |

**结论：Agent 无法为你保留一个常驻服务。** 必须由你自己的会话（explorer → cmd → pythonw）
来启动，它才不被回收。

**正确用法**：

1. **双击 `workbench\启动工作台.cmd`** —— 拉起守护进程并打开浏览器；
   窗口可直接关闭，服务继续在后台跑（要停就在任务管理器结束 `pythonw.exe`）。
2. **或下次登录自动启动** —— `Startup\微信重点工作台.lnk` 已配置（实测可用）。

**已加的健壮性**（因为"悄悄死掉"最难排查）：
- `tools/workbench_supervisor.py` 守护进程：服务退出即自动重启，
  连续快速退出会退避 60s 并记录原因；
- 服务与守护的输出统一写 `out/workbench.log`（含请求异常、绑定失败），
  下次出问题有据可查，不必再靠猜。

## 十三、合规边界（持续遵守）

- 只处理**自己账号**的数据，不用于监控他人。
- 摘要若送云端大模型，等于把别人对你说的话上传第三方；优先本地模型或先脱敏。
