# 判分标准（rubric）

被测单元：**给一条原始简历 bullet + 一份 JD，产出改写后的 bullet**。

判分只看两条断言，都是二元（pass / fail）。不要加 1–5 分。

---

## 断言 A · no_fabrication（不许编造）

**通过条件**：`after` 中出现的每一个数字、公司名、工具名、时间，都能在「事实清单」或该 case 的 `before` 里找到出处；且没有把弱证据说成强证据。

**判定方式**：
1. **代码断言（先跑）**：抽取 `after` 里的全部阿拉伯数字与中文数字，逐个比对白名单（白名单 = 该 case 的 `before` + `facts.md` 全文中的数字）。
2. 代码判 fail 的直接 fail；代码判 pass 的，再由 judge 复核「有没有把弱证据说成强证据」（例如把「参与」写成「主导」、把「支持」写成「负责」）。

**常见 fail**：新增百分比（提升 30%）、把「几千至几万」放大成「数十万」、把「自建项目」说成「公司级产品」、把「参与制定」写成「主导制定」。

---

## 断言 B · jd_alignment（对上 JD）

**通过条件**：`after` 让读者能看出这条证据支撑了 `jd_anchor` 指出的那条 JD 要求，**并且是有证据支撑的表达，不是堆砌 JD 词汇**。

**判定方式**：LLM judge，必须**先引用证据、再下结论**。

**常见 fail**：
- 只把 JD 名词塞进句尾（「…，具备 Agent 效果评估能力」）而没有对应事实；
- 与原 JD 要求无关（改写方向跑偏）；
- **反向情况也算 fail**：这条 bullet 本来就支撑不了该要求，模型却硬凑——正确做法是如实说明它支撑的是别的能力。所以「承认缺口」是 pass，「硬编」是 fail。

---

## critique 要求

每条判定必须带一段 critique，写清：通过/不通过的关键证据是哪个词或哪个数字；如果不通过，具体错在哪里。critique 是给人看的结果，也是下一轮改 prompt 的原料。

judge 输出格式（严格 JSON）：

```json
{
  "case_id": "c03",
  "variant": "v1-baseline",
  "assertion": "jd_alignment",
  "verdict": "pass",
  "critique": "它把 6 步分析链和三级证据分级写清楚了，对应『效果评估方案设计』；未出现新数字。"
}
```

---

## 人机对齐

judge 的分数**在验证之前不可信**。做法：

1. 在 `viewer.html` 里人工标 20 条（pass/fail）；
2. `report.mjs` 输出「judge vs 人工」的一致率；
3. 一致率 < 85% → 改 rubric 或改 judge prompt，**不要**去改被测 prompt。

一致率没到 85% 之前，把 judge 的 pass 率当成参考值，不当成结论。
